# 数据访问、共享状态与取消

用于页面接入接口、建立/调整 service、共享状态或处理请求生命周期。先读实际封装和接口，不能把下面的默认模式当成目标仓库已经实现的 API。

## 领域 service 与统一请求

- service 按业务领域分文件并提供具名函数，入口以命名空间导出。页面示例：`productService.getList(options)`；不是让页面组装 HTTP 配置。
- 已有 fetch/Axios/client/query 接入方式先适配其公共入口；不要因目录规范存在就新建第二套请求基础设施。首次建立统一入口须确认范围，默认名称可为 utils/XRequest.ts。
- XRequest 的对象参数模式包含 url、method、params、data、headers 等实际需要的选项；signal/timeout 或底层额外配置沿用已确认契约，不强加一种参数嵌套。
- 传输层负责 URL/参数/序列化、HTTP 元信息、解析和通用错误。service 负责验证真实字段与领域映射，页面/hook 负责交互和文案。
- service 应返回什么、是否解包 data、是否保留 status/headers，应以真实后端和当前请求入口为准。区分完整响应、JSON body 和 body.data，保持名称、类型与调用方语义一致。
- 状态码通常按入口既有策略处理；特殊业务状态只局部允许并校验其 body，不能全局放行所有错误或把 HTML 错误页当有效领域数据。
- 请求/响应与领域共用类型从 typings/<domain>.ts 显式导出/导入；网络边界为 unknown，按字段/schema 实际校验。缺字段、类型错、无效 JSON 与传输失败应有可分辨结果，不返回伪造成功值。
- 不自动加入认证、Token 续签、下载、轮询、重试或全局通知。若当前接口要求这些能力，在授权范围内显式设计，避免基础设施反向 import 业务 service/store。

## 状态归属

| 状态 | 默认归属 | 提升或变化条件 |
| --- | --- | --- |
| 输入草稿、当前弹窗、按钮 loading | 页面/组件 useState 或 useReducer | 多个页面确需同一生命周期时再共享 |
| 筛选/分页条件 | 所属页面/区块；需可分享或回退恢复时按现有路由放 URL | 编排复杂或复用有明确收益才抽 hook；不维护 URL/state/store 三份真源 |
| 服务端数据 | 所属页面/独立区块，或仓库已选查询缓存 | 不默认每个请求一个 hook；真实缓存、失效、去重需求沿用已有方案 |
| 跨区块焦点 ID、上下文 | 最近共同父层，通过参数和事件协调 | 跨页面/远距消费者确需共享时才用现有 store/Context，生命周期明确 |
| 持久化设置 | 持久化方案中的最小必要字段 | 明确恢复、版本/清理；临时 loading/error 不持久化 |

- 已选择 Zustand 时，可参考按领域 store、具名 actions、选择器订阅：视图只订阅需要的字段，事件可调用 actions/getState；不把全部 store 当 props 广播。
- actions 可以协调 service，但纯转换工具不能依赖 store；衍生状态优先推导，不重复维护需要双向同步的缓存。
- 沿用现有状态方案，不为简单页面安装 Zustand、Redux、查询库或 persist/devtools；持久化也不能保存凭证或无关业务数据。
- 清晰区分 UI 状态与接口 DTO。表单提交时显式转换字段；已提交后的列表刷新/失效按已选缓存方案处理。
- 已有请求 hook 可按真实 API 使用，不强制引入 ahooks 或保留某种实例写法；无库时 useState/useEffect 的简单实现有效。加载/错误归属实际按钮/区块，不用一个全局 busy 掩盖全部流程。
- 通信传必要 ID/明确语义参数，焦点对象从当前数据推导；列表更新后确认选中仍有效。上报保存成功后调用实际刷新/缓存失效入口，不为父层已有请求制造无意义 refreshKey 通信；已有查询键/显式 revision 若有真实用途不机械禁止。

## 请求生命周期与取消

- 页面卸载、参数切换或刷新替换时清理所属请求；为每次请求保留身份/序号，旧响应即使未被底层及时取消也不能覆盖新数据、错误或 loading。
- 外部 signal 必须继续有效，外部已取消不能被新 controller 变成未取消。signal 传到真实传输层；本地只改状态不算取消请求。
- 超时、主动取消、HTTP/网络失败、解析/契约错误分开处理。主动取消通常不展示为新故障；实际超时要结束 loading，提供恢复操作。
- 先取消被替换的旧请求，再登记新请求；完成/失败均清理 timer、监听器与注册记录。错误路径不得留下不 settle 的 Promise。
- 若已有集中管理器，保留其 setFlag/abort/clearController 等公共用法。登记 opts 后使用返回 signal，最终在 finally 清理；登记须主动选择范围，不能照搬旧业务白名单或模糊 URL includes。
- 同 URL 多消费方使用唯一 abortKey、消费方 scope 或独立管理器。页面卸载不能调用共享管理器的无参 abort-all，避免影响其他页面。
- 只有 URL key 的管理器需要显式 scope 策略；清理按 controller/请求身份，不按可能已改写的 URL 查找。重复清理安全，完成旧请求不误删新记录。
- `abort(key, true)` 若约定为取消组内最新请求，不等同“保留最新”。沿用真实 API 含义；注册新请求后再调用该方法可能取消新请求。
- 独立并发检查分别保留结果；有依赖关系的步骤按依赖执行，不为了并发使条件未验证的数据流入下一步。

## 验证与降级

- 先测相关失败行为再实现：参数/响应校验、传输异常、特殊状态与非法 body、外部 signal、清理、重复取消、消费方隔离、旧结果保护、失败后恢复。
- 工具单测不等于传输接入完成：对实际 client 验证 signal 传递与 finally，页面层验证切换/卸载/重试后的状态。
- 测试按仓库已有工具运行；没有相应环境时说明未验证的路径，不宣称服务接通或部署成功。
- 接口缺失时，输出文件职责、交互状态、契约问题及待提供项，停止受阻接入。没有真实路径不能编造 endpoint；路径已知但字段未知也不能用断言假装完成。业务 mock/demo 仅在用户明确授权时使用；测试 fixture/注入 loader 可用于验证，须与正式接入区分，不能把它说成真实接口。
